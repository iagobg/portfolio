## What I wanted to build

I built Live Trivia around a simple interaction: a host runs a quiz while everyone else joins from their own phone. I wanted the room to feel shared, with people seeing each other type and react, while the server kept timing and scoring consistent.

The host can create a room, load a quiz, and control the rounds. Players choose a name and color, submit guesses, receive hints, and follow the scores through to the final podium.

## Keeping the game in one place

I used Phoenix LiveView for the screens and an OTP process for each room's game state. That gave me one place to handle questions, timers, guesses, scores, and round transitions.

A detail I had to account for was resetting a round while old timer messages were still waiting to be processed. I attached a round identifier to scheduled work so a stale hint or timeout could not affect the next round.

<Decision title="The server decides">I kept the game rules on the server. Browser effects can make the room more expressive, but they should not decide whether a guess counts or when a round ends.</Decision>

I also wanted near misses to mean something. The scoring logic uses Levenshtein distance to classify guesses, and the closest answer can receive consolation points if nobody gets an exact match before time runs out.

## Making the room feel alive

The typing bubbles were an important part of the experience I was building. They let players see activity around the shared stage instead of waiting silently for a score update.

I initially leaned on LiveView for the whole interaction. As the typing behavior grew, I separated two different responsibilities: deciding the game state and showing frequent visual updates.

| What changes | How I handle it |
| --- | --- |
| Questions, rounds, hints and scores | The room process owns state; PubSub and LiveView distribute and render updates |
| Players and reserved colors | Phoenix Presence tracks occupancy |
| Typing bubbles | Phoenix Channels carry frequent text previews outside the LiveView diff loop |

Moving typing traffic to Channels let me work on its payload and update rate without changing the rules of the game.

## Giving performance work a repeatable target

I built an admin-triggered synthetic benchmark so I could exercise the typing path with 16 simulated players instead of relying on a room that merely felt responsive during manual use.

The benchmark creates a room, loads demo questions, and records browser and server measurements. I can inspect message rate, payload size, handler timing, memory and CPU samples alongside browser latency and DOM timings.

That gave me a practical way to evaluate client-side throttling and more compact payloads. I moved identifiers toward compact slot-based values and added a binary typing path.

<Decision title="Measure the path being changed">I wanted to compare transport changes without replacing the server-authoritative model. The synthetic room gives me a repeatable workload for that comparison.</Decision>

I treat those measurements as workload-specific. The host, build and sampling window matter, and a 16-player synthetic room does not establish production capacity.

## Designing for the phone keyboard

The desktop stage did not translate directly to a narrow screen. I gave the player view a compact roster and mobile-specific bubble positions so the phone still felt connected to the room.

The keyboard was another constraint. I used visual-viewport hooks and CSS variables to keep the answer input usable when the keyboard opened, rather than assuming the browser's full height was always available.

I also reserved colors and player slots during entry. That keeps two people joining at the same time from claiming the same available identity.

## Keeping the scope manageable

I chose bounded, in-memory rooms for live sessions rather than adding a database and long-lived game history. The room lifecycle handles creation, passwords, occupancy and cleanup.

| Responsibility | Implementation |
| --- | --- |
| Room state | One `LiveTrivia.Game` GenServer per room |
| Room lifecycle | `LiveTrivia.Lobby` |
| Shared updates | Phoenix PubSub and Presence |
| Interface | Phoenix LiveView with browser hooks |
| Delivery | Docker releases and GitHub Actions |

For deployment, I used a Docker release image published to GHCR and a targeted Docker Compose redeploy. Updating Live Trivia should not restart the other services sharing the host.

## What I took away

The most useful distinction I made was between game decisions and visual activity. LiveView remains responsible for the shared interface, while Channels handle the lightweight traffic that makes typing feel immediate.

Building the benchmark also changed how I approached optimization. It gave me something specific to compare: bytes sent, work performed, and time spent along the typing path.

Live Trivia is deployed, with host controls, phone participation, timed rounds, hints, scoring and a final podium. Its scope is deliberately focused on a live session. The part I care most about is how those pieces come together: one host can run the room while players see the game—and each other—respond.
